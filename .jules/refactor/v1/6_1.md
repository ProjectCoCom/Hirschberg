Once a multi-task workflow's individual branches have all merged into a shared integration
branch, review the combined result for cross-agent issues before the final PR to the real
target branch — using a dedicated integrator-role account, not QA.

CONTEXT
merge_review.py is a full integration pipeline: merge_branches() combines every task's
individual branch into one create_integration_branch() result, run_review_session() reviews
that combined branch, cleanup_branches() removes the individual branches, and
create_final_pr() opens the one PR that goes to the real target. This is a genuinely
different job than Step 6's QA gate — QA reviews one task's diff in isolation before it
merges into the integration branch; this reviews what happens when several agents' work
gets combined, which is invisible from any single diff. They're complementary, not
competing, and Step 6 doesn't change as a result of this step.

The real problem worth fixing: run_review_session()'s prompt currently includes "fix any
conflicts or broken imports" — this reviewer is allowed to silently patch the integration
branch with nothing re-reviewing what it changed before create_final_pr() ships it. That's
the same shape of problem QA was built to prevent, one level up. Every function in this file
is also a raw httpx call straight to GitHub's API, bypassing clients/github.py entirely —
same fix as everywhere else this pattern has shown up.

REQUIREMENTS
- Add AccountRole.INTEGRATOR to the enum in account_pool.py, following the same pattern
  ORCHESTRATOR/WORKER/QA already established in Step 3.
- For workflows with more than one task: create the integration branch once, at workflow
  dispatch time (workflow_engine.py's run(), before any tasks are dispatched), based off the
  real target branch's current SHA. Persist it (a field on the workflow, e.g.
  workflows.integration_branch).
- Extend the per-task branch-creation helper Step 4 added to clients/github.py to accept an
  optional base branch, defaulting to the workflow's integration branch when one exists,
  falling back to the real target branch otherwise. For single-task workflows, skip the
  integration branch and this whole step entirely — there's nothing to integrate, and Step
  6's existing per-task gate already merges straight to the real target correctly. Don't add
  integration-branch overhead where there's only one branch.
- Task branches merging on QA approval (Step 6, unchanged) naturally merge into the
  integration branch instead of the real target for multi-task workflows, simply because
  that's the target they were given — no Step 6 code needs to change for this to be true.
- Once every task in a multi-task workflow has reached COMPLETED with its branch merged into
  the integration branch, dispatch an integrator-role session against that combined branch.
  Prompt: same adversarial, report-only, never-writes-code discipline as QA's reviewer
  prompt, but checking for cross-agent integration issues specifically — broken imports
  between what different agents touched, duplicated or conflicting implementations,
  contradictions between tasks — with each contributing task's exit_criteria included as
  reference. Remove the "fix any conflicts or broken imports" instruction entirely; this
  session never writes code, same as QA. Same structured verdict format as QA
  (approve/reject + blocking_issues).
- On integrator approval: create_final_pr() opens the PR from the integration branch to the
  real target. Extend the state-lookup-by-identity pattern Step 6 already established for
  merge eligibility to also recognize integrator verdicts for PRs whose head branch is a
  known integration branch — this PR goes through the exact same auto_merge.py gate as every
  other merge path (CI green AND verdict approve), not a separate one.
- On integrator rejection: send the blocking issues to the responsible orchestrator session
  via Step 5's sendMessage mechanism, same as a QA rejection — the orchestrator decides on a
  corrective task; the integrator never patches anything itself.
- Only after the final PR is confirmed merged, run cleanup_branches() to remove the
  individual task branches — never before a confirmed successful merge.
- Route merge_branches(), create_integration_branch(), cleanup_branches(), and
  create_final_pr() through clients/github.py instead of raw httpx calls.

CONSTRAINTS
- Single-task workflows never create an integration branch and never dispatch an integrator
  — Step 6's existing behavior for them is unchanged.
- Integrator sessions never write code, exactly like QA.
- cleanup_branches() only fires after a confirmed successful final merge, never speculatively.

ACCEPTANCE CRITERIA
- A workflow with 3+ tasks: each task's branch merges into a shared integration branch after
  individual QA approval; once all are in, an integrator session reviews the combined
  branch; on approve, one final PR opens and merges through the standard gate; individual
  task branches are cleaned up only after that final merge is confirmed.
- A single-task workflow behaves exactly as Step 6 already specifies on its own — no
  integration branch, no integrator dispatched.
- An integrator reject routes blocking issues to the orchestrator and does not open the
  final PR.
- No raw httpx calls remain anywhere in this pipeline.
