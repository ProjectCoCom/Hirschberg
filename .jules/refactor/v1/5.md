Give the standing orchestrator session visibility into what its dispatched tasks are doing,
without stopping unrelated work every time one thing fails.

CONTEXT
Neither coordinator.py's _poll_session nor session_runner.py's _poll_until_done ever calls
Jules's sendMessage — both are one-shot "create, poll to a terminal state, return" loops.
clients/jules.py already implements send_message(session_id, prompt) — the client-level
capability exists, nothing calls it yet.

workflow_engine.py's run() currently cancels every other running task in the workflow the
moment any single task reaches FAILED — full workflow-wide cancellation, no distinction
between a failure that actually blocks a sibling and one that doesn't.

session_runner.py's _store_activity() always writes raw_data: {} — the schema has the column,
nothing populates it.

system_prompts.py's JULES_QUESTION_HANDLER currently answers a worker's mid-task question via
the ai_providers pool. With Jules as the orchestrator, that becomes the standing
orchestrator's call instead — plan_executor.py's _answer_jules_question() is the real call
site, retired as part of Step 4.

REQUIREMENTS
- Change workflow_engine.py's failure handling from workflow-wide cancellation to
  dependency-scoped cancellation: when a task reaches FAILED, cancel every task that
  transitively depends on it — the full closure, including tasks that only depend on it
  through another task that's just been cancelled, not only direct dependents — while
  independent branches keep running.
- Add a notify_orchestrator() call, fired once per state transition (not once per poll
  tick), when a tracked task reaches COMPLETED, FAILED, PAUSED, or AWAITING_USER_FEEDBACK.
  Hook this into coordinator.py's _poll_session for DAG-run tasks and session_runner.py's
  _poll_until_done for the standing orchestrator's own session — track last-seen state
  independently in each loop for now; Step 13 will consolidate this when it merges the two
  polling implementations. Include task id/description, resulting state, PR URL if any, and
  a short summary — not the full diff.
- Call the existing JulesClient.send_message(session_id, prompt) to deliver the digest above
  to the standing orchestrator's session id.
- Route a worker session reaching AWAITING_USER_FEEDBACK to the standing orchestrator via
  sendMessage, including the worker's question and enough context to identify which task
  it's about. Watch specifically for the orchestrator's next agentMessaged activity (not any
  new message generically — a userMessaged entry could be unrelated human input) and relay
  its content back to the worker session via sendMessage on the worker's session id.
  Serialize this per orchestrator session: don't send a new notification to a given
  orchestrator while a previous one is still awaiting a reply — queue it instead. Without
  that, "the next agentMessaged activity" stops being a safe way to identify which question
  it's actually answering.
- Fix _store_activity() in session_runner.py to actually populate raw_data with the real
  activity content instead of {}. Step 6's QA-verdict parsing and Step 7's audit trail both
  need this.
- Add orchestrator_session_id as a string column on agent_tasks (and a matching field on the
  AgentTask Pydantic model) to persist which standing orchestrator is responsible for which
  task — task-level, not workflow-level, since Step 8 lets a sub-orchestrator own part of a
  workflow while another orchestrator owns the rest. Index this column — the notification
  path above will be querying by it often enough that an unindexed lookup would repeat the
  same pattern Step 12 already had to fix elsewhere. Expose save_task_orchestrator() and
  get_task_orchestrator() on ContextStore for this.

CONSTRAINTS
- The relay makes no decisions from digest content — it only delivers it and relays the
  reply. Whatever happens next is the orchestrator's call.
- Preserve existing single-task polling behavior exactly when there's no standing
  orchestrator to notify (the static workflow_parallel.json CLI path) — notification is
  additive.

ACCEPTANCE CRITERIA
- A task with two independent siblings and one dependent: failing one sibling cancels only
  the dependent (and anything that depends on the dependent, transitively), not the
  independent sibling.
- Completing a tracked task fires exactly one sendMessage to the correct orchestrator
  session; two rapid transitions don't duplicate it.
- A worker session entering PAUSED also notifies the orchestrator, same as COMPLETED/FAILED/
  AWAITING_USER_FEEDBACK.
- A worker session entering AWAITING_USER_FEEDBACK results in a message to the orchestrator
  and, once it replies, a sendMessage back to the worker — with no ai_providers call
  anywhere in that path. Two workers asking questions of the same orchestrator around the
  same time don't get each other's answers.
- raw_data on a newly stored session_activities row contains the real activity payload, not
  {}.
- get_task_orchestrator() for a given orchestrator session runs against an indexed lookup,
  not a full table scan.
