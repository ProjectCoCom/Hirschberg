## Step 14 — Reduce auto_merge.py's check-polling overhead

Cut the number of GitHub API calls auto_merge.py makes per merge by backing off instead of
polling at a fixed interval, and fix a retry gap on the one call that matters most.

CONTEXT
auto_merge.py's _wait_for_checks() polls list_check_runs() every CHECK_POLL_INTERVAL (30
seconds) for up to CHECK_TIMEOUT (600 seconds) — 20 GitHub API calls for a single merge's
check-wait, even though most of that waiting time is CI actually running, not something that
needs checking every 30 seconds. With multiple PRs merging around the same time (worker + QA
+ the Step 6.1 integrator, all producing/reviewing PRs in parallel), this adds up against
GitHub's per-token rate limit — a shared budget across the whole app, not per-session.

clients/github.py already has rate-limit awareness (_check_rate_limit()) and wraps
get_pull_request, list_check_runs, and list_pr_comments in a tenacity-based @_retry decorator
— but merge_pull_request itself isn't decorated. That's backwards: the read-only polling
calls retry automatically, but the merge itself doesn't, so a transient 5xx on a fully
approved, QA-passed, CI-green PR fails outright instead of retrying.

No webhook infrastructure exists in this codebase, so backoff is the pragmatic fix, not
webhooks (which would be new infrastructure — a publicly reachable endpoint, signature
verification — not a small addition).

REQUIREMENTS
- Apply adaptive backoff to _wait_for_checks(): initial_interval=15.0, multiplier=1.5 (same
  shape as Step 13's SessionPoller, deliberately — no reason to invent a second curve),
  max_interval=90.0, same 600s CHECK_TIMEOUT. Not a lower initial interval: CI checks
  realistically never resolve in under 20-30 seconds (runner startup and checkout alone
  usually exceed that), so starting faster doesn't buy real responsiveness, only spends
  calls on a window where the answer is predictable. This schedule works out to ~10 total
  polls per full-duration wait, versus 20 under the old flat interval — verify this
  arithmetic directly in a test rather than trusting it by inspection.
- Add jitter (±10%) to each computed interval — more important here than in Step 13's
  session polling, since multiple PRs (worker, QA, the Step 6.1 integrator) can be
  check-waiting concurrently against GitHub's single shared rate limit, not independent
  per-session budgets. Synchronized polling against a shared budget is worse than
  synchronized polling against independent ones.
- Optional: cap the final sleep interval to the exact remaining time before CHECK_TIMEOUT is
  reached, so total wait never exceeds 600s even slightly. Not required — the original flat-
  interval code didn't guarantee this either, it only appeared to by coincidence of 600 being
  evenly divisible by 30 — but cheap to add if you'd rather have the tighter guarantee.
- Add the @_retry decorator to merge_pull_request() in clients/github.py, matching the same
  pattern already used on the other methods in that file.
- Tests: mock two consecutive transient 5xx responses on merge_pull_request() and confirm the
  third call succeeds, directly validating @_retry's actual configured behavior. Separately,
  test the backoff schedule itself — assert the actual sequence of intervals (or total call
  count over a simulated full-duration wait) matches the intended curve, not just that the
  function eventually returns. Location: pending confirmation of this project's actual test
  conventions (see below) — don't guess a structure independently of that.

CONSTRAINTS
- Don't change what counts as a passing/failing check set — only how often status gets
  checked and whether the merge call itself retries on transient failure.
- Don't build webhook infrastructure as part of this step — that's a bigger, separate
  decision if you want it later.

ACCEPTANCE CRITERIA
- A check-wait that resolves quickly (checks complete within the first poll or two) is
  detected with comparable or better latency than the old flat-30s version, not worse.
- A full-duration (timeout-length) check-wait uses ~10 total polls, versus the old flat
  interval's 20 — verify against the actual number, not just "fewer than before."
- A simulated transient 5xx on the merge call itself now retries instead of failing outright.
