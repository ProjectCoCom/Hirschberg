## Step 4 — Consolidate onto one execution engine

There are two independent, non-integrated systems for running Jules tasks in this codebase.
Consolidate onto the one with persistence, retries, and dependency-aware parallelism, and
retire the other's execution machinery.

CONTEXT
System A: workflow_engine.py + coordinator.py + account_pool.py + clients/jules.py +
context_store.py. Accounts sourced from the accounts table via config_loader.build_jules_pool()
(Step 3). Tasks persisted to agent_tasks/workflows via the shared db interface. Proper retries
(tenacity), proper connection reuse (per-account cached JulesClient), dependency-aware parallel
execution, and — once Steps 2, 3, 5, 6, 7, 9, 11, and 13 land — local-DB backed, role-aware,
capacity-aware, QA-gated, and backpressure-safe. Every other step in this document builds on
top of this system.

System B: core/plan_executor.py, triggered via /api/execute — previously unlocated despite
checking api/chat.py (confirmed to only save drafts, never execute) and api/plans.py
(confirmed plain CRUD, no execute action). parse_plan() reads the same JSON shape
PLAN_MODE_SYSTEM/AUTO_MODE_SYSTEM produce:

    {
      "tasks": [
        {
          "id": "agent-1",
          "description": "What this agent does",
          "prompt_id": "skill-name-from-available-skills-or-null",
          "dependencies": [],
          "exit_criteria": "How to verify this is done",
          "branch": "jat/agent-1-description"
        }
      ],
      "execution_mode": "hybrid"
    }

into plan_executor's own lightweight AgentTask dataclass — structurally different from
models/workflow.py's AgentTask (string IDs vs UUIDs, no workflow_id/parent_task_id/
account_id, no TaskStatus enum). From there, System B runs entirely on its own:
- get_jules_key() picks an account by querying the accounts table directly and taking
  whichever enabled row has the lowest sessions_today — no role awareness, no source
  matching, nothing from account_pool.py. Once Step 3's role column exists, this function has
  no way to know it does.
- create_jules_session(), send_message_to_session(), _approve_plan(), poll_session_status(),
  and _fetch_recent_activities() all make raw httpx calls straight to
  https://jules.googleapis.com, duplicating clients/jules.py's JulesClient with less
  robustness — most have no retry logic at all.
- poll_session_status() is a fourth independent session-polling loop, on top of the two Step
  13 consolidates and the mcp/server.py call site Step 13 confirmed delegates to one of them.
- poll_session_status() auto-approves every AWAITING_PLAN_APPROVAL unconditionally — no
  condition, no human involved. This is the exact state Step 7 adds human gating for. Left
  running, Step 7's gate does nothing for anything dispatched through System B.
- poll_session_status() answers a worker's mid-task question via _answer_jules_question(),
  which calls the ai_providers pool directly. This is the real call site Step 5 redirects.
- None of System B's task execution touches agent_tasks, workflows, context_messages, or
  session_activities — only accounts.sessions_today gets written. Nothing dispatched this way
  is visible to the dashboard's task views, Step 7's audit trail, or Step 6's QA gate.
- create_jules_session() builds its prompt directly, without going through prompt_builder.py
  — sessions dispatched this way never get the rules/gates/anti-patterns/context injection
  Step 16 caches. They get a bare prompt.

Beyond /api/execute itself, get_jules_key(), create_jules_session(), poll_session_status(),
and reset_daily_sessions() are also imported by api/server.py (recovery/reset loops),
core/merge_review.py (review sessions — likely the actual implementation behind the
post-merge reviewer flagged in Step 6), core/auto_mode.py, and mcp/server.py. Retiring these
functions has a wider blast radius than /api/execute alone.

Recommendation: retire System B's execution machinery — get_jules_key(),
create_jules_session(), send_message_to_session(), _approve_plan(), poll_session_status(),
_fetch_recent_activities(), and _answer_jules_question() — and keep only parse_plan() for
what it's actually good at: turning the chat interface's JSON output into structured data.
Retarget that output at models/workflow.py's Workflow/AgentTask shape and hand it to
workflow_engine.py instead of driving a second, weaker execution path.

REQUIREMENTS
- Add assign_to: str (account name or label) to the plan JSON shape above. Everything else
  (id, description, dependencies, exit_criteria, branch, prompt_id, execution_mode) stays
  exactly as-is.
- Change parse_plan() to build models/workflow.py's Workflow/AgentTask objects — translating
  string dependency references like "agent-1" into the UUID-based depends_on list once real
  task UUIDs are assigned — instead of plan_executor's own AgentTask dataclass.
- Redirect /api/execute to build a Workflow from parse_plan()'s output and hand it to
  workflow_engine.run(), instead of looping through create_jules_session().
- Resolve assign_to through the role-aware account_pool.py (Step 3). This is a hard
  requirement, not a preference: if assign_to names a specific account or label and no
  matching account is enabled and has capacity, acquire() raises AccountPoolExhausted — don't
  silently fall back to a different available worker the orchestrator didn't ask for.
- System A doesn't currently create git branches or update .jules/jdocs/context.xml before/
  after a task runs — System B's create_branch_from_ref() did this. Add a small helper in
  clients/github.py (not inline in coordinator.py) that creates the task's branch before
  dispatch, using a GitHub token passed through from wherever /api/execute already has one.
  For JDOCS specifically: check whether coordinator.py currently builds task prompts via
  prompt_builder.build_session_prompt() or its own separate prompt construction. If it's the
  latter, switch it to build_session_prompt() — JULES_MASTER_PROMPT already instructs the
  agent to update JDOCS itself as part of its own work, so this is likely the entire fix, not
  new orchestration logic.
- Delete get_jules_key() and poll_session_status() outright — don't preserve slimmed-down
  versions of either. They're not just old code, they contain the two specific bugs (no role
  awareness, unconditional auto-approve) this consolidation exists to fix; a smaller version
  that keeps either property just hides the bug one layer deeper.
- Refactor mcp/server.py's imports to use JulesClient/AccountPool now, as part of this step.
- For api/server.py, core/merge_review.py, and core/auto_mode.py: repoint their imports to
  JulesClient/AccountPool so they keep working, but don't redesign what they do as part of
  this step. core/merge_review.py's actual behavior (whether it should be replaced by Step
  6's QA role, kept alongside it, or something else) is Step 6's decision, not this one. If
  auto_mode.py or api/server.py turn out to have their own polling loops or their own
  account-selection logic — plausible, given the pattern everywhere else in this codebase —
  flag that clearly rather than fixing it here; it belongs with Step 13 or Steps 9/11
  respectively.
- Route reset_daily_sessions() callers to account_pool.py's existing daily_tasks_used/
  daily_reset_at mechanism instead — that already does the same job.
- Widen AgentTask.context from dict[str, str] to dict[str, Any] in src/models/workflow.py, so
  Step 6's QA verdict can store structured data directly.
- Add the columns this step needs (assign_to, prompt_id, exit_criteria on agent_tasks;
  execution_mode on workflows) directly into Step 2's schema file, the same way every other
  schema change in this build order works. Don't add them via runtime "check for missing
  column, alter table if absent" logic in local_db.py — that scatters what the schema actually
  is across implicit startup behavior instead of one reviewable file. If Step 2 has already
  run against a database with real data in it, write a proper follow-up migration file
  instead, matching whatever numbered-migration convention the project already uses.

CONSTRAINTS
- Don't touch how dependencies already resolves within workflow_engine.py — only add the
  assign_to -> account_id resolution and the parse_plan() retargeting.
- Malformed or partial plan output should log and wait for a corrected version, not crash
  anything downstream.
- Don't redesign core/merge_review.py's, core/auto_mode.py's, or api/server.py's actual
  behavior as part of this step — import repointing only. Flag anything that looks like it
  belongs to a later step instead of fixing it inline here.
- If retiring System B's execution functions breaks something not visible from the files
  inspected so far, stop and flag it rather than silently working around it.

ACCEPTANCE CRITERIA
- A plan dispatched via /api/execute results in real Workflow/AgentTask rows in
  agent_tasks/workflows, executed by workflow_engine.py with dependency-aware parallelism —
  not plan_executor's own loop.
- assign_to correctly resolves to account_id via the role-aware pool, and raises
  AccountPoolExhausted rather than substituting a different account when the named one isn't
  available.
- A plan dispatched this way creates its task branches, gets its JDOCS updates (via
  build_session_prompt(), confirmed not new orchestration code), and is visible in the same
  places a workflow_parallel.json-driven run already is: agent_tasks rows, session_activities
  rows, dashboard task views.
- get_jules_key() and poll_session_status() are gone, full stop — no slimmed-down versions.
- mcp/server.py, api/server.py, core/merge_review.py, and core/auto_mode.py all still run
  without error against JulesClient/AccountPool, with no behavior changes beyond that swap.
- agent_tasks and workflows have the new columns present via the schema file, not added at
  runtime.
