Define how a standing orchestrator session actually comes into being, give a human a review
gate on its plans specifically, and make its decision history visible without building new
UI.

CONTEXT
clients/jules.py's create_session() already accepts require_plan_approval: bool = False, and
approve_plan(session_id) is already implemented. Neither coordinator.py's _poll_session nor
session_runner.py's _poll_until_done handle AWAITING_PLAN_APPROVAL as a state — anything
outside {COMPLETED, FAILED, PAUSED} just keeps polling until SESSION_TIMEOUT (30 minutes) and
returns a timeout result.

Nothing in this document so far specifies how a standing orchestrator session is actually
created. agent_tasks.orchestrator_session_id (Step 5) records which orchestrator is
responsible for a given task, but nothing tracks orchestrator sessions as records in their
own right — there's no table, no creation path, nothing to point that column at until one
exists independently of any task.

Confirm Step 4 has actually landed before this step runs: plan_executor.py's
poll_session_status() — retired in Step 4 — auto-approves every AWAITING_PLAN_APPROVAL
unconditionally, with no human involved. If it's still running, this step's approval gate
does nothing for anything dispatched through that path.

REQUIREMENTS
- Add an orchestrators table: session_id (text, primary key — the Jules session id itself,
  no separate synthetic key needed), account_id (fk to accounts), repo_owner, repo_name,
  goal (free text), status, seed_plan_id (nullable fk to plans, if this orchestrator started
  from a chat-drafted plan), parent_orchestrator_session_id (nullable, self-referential —
  unused until Step 8, but cheap to add now rather than migrate later), created_at,
  updated_at. status is a small enum of its own (e.g. OrchestratorStatus: active,
  awaiting_plan_approval, completed, failed) — not TaskStatus; an orchestrator session is not
  an agent_tasks row and shouldn't be modeled as one.
- Add a creation endpoint (api/orchestrators.py, matching the api/chat.py and api/plans.py
  naming convention — confirm against however routers actually get registered in this
  project) — POST /api/orchestrators, accepting a target repo, a goal, and an optional
  seed_plan_id. It acquires an orchestrator-role account (Step 3's account_pool.py), builds
  an initial prompt (either "here's a draft plan sketched via chat: {plan_json} — review,
  refine, and begin dispatching tasks" if seeded, or "your goal: {goal} — break this down and
  begin dispatching tasks" if not), creates the session with require_plan_approval=True, and
  inserts the resulting orchestrators row.
- In both polling loops, on AWAITING_PLAN_APPROVAL: look up the orchestrators row for this
  session_id, set its status to awaiting_plan_approval, and notify via Step 5's mechanism.
  Do not call approve_plan() from within the polling loop — keep polling normally afterward,
  waiting for the session to naturally transition once approval happens through the endpoint
  below. As a cheap defensive check: if this state is ever seen on a session_id that isn't in
  the orchestrators table, log a warning — it should be structurally impossible (worker tasks
  never set require_plan_approval), and if it happens, something upstream set the flag
  somewhere it shouldn't have.
- Add a separate endpoint (e.g. POST /api/orchestrators/{session_id}/approve-plan) that calls
  the now-retried approve_plan(session_id) directly and updates the orchestrators row's
  status back to active on success.
- Wrap approve_plan on JulesClient with the @_retry decorator, matching the pattern already
  used on most of that file's other methods.
- Add GET /api/orchestrators/{session_id}/history returning that orchestrator's
  session_activities rows in order, joined with the agent_tasks it's dispatched (via
  orchestrator_session_id) — this is a read over data Steps 4 and 5 already persist, not new
  storage.
- Expose a pending-approval count (a simple COUNT(*) on orchestrators where status =
  awaiting_plan_approval) — add it to whichever existing dashboard-state endpoint already
  aggregates session data for the frontend (get_ui_state is a reasonable guess; confirm
  against what the dashboard actually polls before adding a new endpoint for just this).

CONSTRAINTS
- No new dashboard page or visual design — expose the data, keep presentation minimal.
- Don't build Step 8's sub-orchestrator delegation here — parent_orchestrator_session_id
  exists on the schema now so it doesn't need a later migration, but nothing populates it
  until Step 8.

ACCEPTANCE CRITERIA
- POST /api/orchestrators creates a session with require_plan_approval=True and a matching
  orchestrators row, seeded correctly from a plans row when one is given.
- An orchestrator session's first plan requires explicit approval before it can dispatch
  anything, and actually resumes on approval via the dedicated endpoint rather than the
  polling loop calling approve_plan() itself.
- AWAITING_PLAN_APPROVAL on a session with no matching orchestrators row logs a warning.
- GET /api/orchestrators/{session_id}/history returns that orchestrator's activity and
  dispatched-task history correctly, using only already-persisted data.
- The pending-approval count is visible somewhere in the existing dashboard-state response.
