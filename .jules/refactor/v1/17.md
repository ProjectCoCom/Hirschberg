Give every file a descriptive header explaining its purpose, and generate a machine-readable
map of the whole repository so future agents can navigate it without guessing at paths.

CONTEXT
This entire document is proof of the problem it's solving: every file referenced in it was
found by guessing plausible names, fetching, and correcting course when the guess was wrong.
A description per file plus one map of the repo would have turned most of that into a single
lookup.

SCOPE
Applies to every file the project actually authors and maintains: .py, .json (config/data
files, not lock files), .sql, .sh/.bat, .yaml/.yml, and frontend source files. Excludes
dependency directories (node_modules, .venv, site-packages), lock files (uv.lock,
package-lock.json, pnpm-lock.yaml), build output, .git, and anything tool-generated rather
than hand-authored. Use this same exclusion list for both parts below — don't let them drift
apart from each other.

PART A — File header comments

REQUIREMENTS
- Every applicable file gets a header, in whatever comment syntax that file type supports,
  with three consistent parts every time:
    1. One-line summary of what this file is.
    2. What it actually does — main responsibilities, 2-4 sentences or a short list.
    3. How it fits in — what it depends on, what depends on it, or which files it's tightly
       coupled to, when that's not obvious from its location alone.
  Keep this structure identical across every file so the results are scannable and
  comparable, not freeform per file.
- .py files: a module-level docstring at the top, before imports.
- .sql, .sh: native comment syntax for that file type.
- Already-prose .md files (README.md, this document, etc.): skip — they already describe
  themselves. This is for source and config files, not documentation.
- .json files have no native comment syntax — add a reserved top-level key, "_description",
  whose value is the same three-part summary as one string. Use this exact key name
  everywhere. Confirm nothing in the codebase does strict schema validation on these files
  that would reject an unrecognized key; if something does, either allowlist the key there
  or use whatever metadata mechanism that validator already supports instead.

CONSTRAINTS
- Comments and one metadata key only — no behavior changes to any file.
- Don't touch excluded paths.

ACCEPTANCE CRITERIA
- Every non-excluded file has a header matching the three-part structure.
- Every non-excluded .json file has a "_description" key, and the application still starts
  and runs correctly with it present.

PART B — docs/map.json

REQUIREMENTS
- Add a script (wherever this project's existing scripts/ directory convention points) that
  walks the repo, applying Part A's exclusion list, and generates docs/map.json as a flat
  list, one entry per file:
    {
      "path": "src/core/account_pool.py",
      "raw_url": "https://raw.githubusercontent.com/ProjectCoCom/Hirschberg/refs/heads/development/src/core/account_pool.py",
      "description": "<the one-line summary from that file's Part A header>"
    }
  Part A must run first, since "description" is pulled directly from what it wrote — sequence
  these two parts in that order within this step, not in parallel.
- Derive owner/repo/branch for raw_url from git itself (remote origin, current branch) rather
  than hardcoding this repo's current name — the map should regenerate correctly if this
  moves or gets forked again, not need hand-editing every time.
- Make the script safely re-runnable: running it again after files are added, removed, or
  renamed produces a correct, complete map, not a stale or duplicated one.
- Add a check to whichever CI workflow already exists in .github/workflows/ (inspect first)
  that fails if docs/map.json is out of date relative to the actual file tree — otherwise
  this goes stale the first time someone adds a file and forgets to regenerate it, and stops
  being trustworthy for exactly the use case it exists for.

CONSTRAINTS
- docs/map.json is itself generated output — exclude it from Part A's header requirement and
  from its own listing.

ACCEPTANCE CRITERIA
- docs/map.json exists, includes every non-excluded file with a correct path, working raw
  URL, and non-empty description.
- Deleting a file and re-running the script removes it from the map; adding a file and
  re-running adds it, description pulled from that file's own Part A header.
- The CI check fails on a deliberately stale map and passes once regenerated.
