## Step 13 — Consolidate session polling into one shared engine

Replace coordinator.py's _poll_session and session_runner.py's _poll_until_done — two
separate implementations of the same "poll a session to a terminal state" loop — with one
shared engine, and give it adaptive backoff instead of a fixed interval.

CONTEXT
Both loops do fundamentally the same thing: call get_session() and list_activities() on a
timer, store new activities, and return once the session reaches a terminal state. They
differ in interval (coordinator.py polls every 30 seconds, session_runner.py every 15) for no
stated reason, and any fix has to be applied twice.

Note: coordinator.py's original _poll_session never stored individual activities at all —
only session_runner.py's loop did. Unifying onto one engine means coordinator.py's DAG-task
path will start populating session_activities for the first time. This is intentional and
correct, not an incidental side effect — Step 6's QA verdict parsing and Step 7's audit trail
both read from session_activities, and without this, every task running through the DAG
engine (the primary path once Step 4 lands) would be invisible to both. The extra write
volume this creates is exactly what Step 10's WAL-mode work was already sized for.

mcp/server.py's jat_run_session tool was a candidate for a third independent implementation,
but it isn't — it calls core.session_runner.run_session() directly, so it's already covered
by whatever this step does to session_runner.py.

plan_executor.py's poll_session_status() is a real fourth one, but it isn't being folded in
here — Step 4 retires it entirely as part of retiring System B's execution machinery. If
Step 4 hasn't landed yet when this step runs, confirm that first.

REQUIREMENTS
- Extract the shared logic into one polling engine (e.g. src/core/session_poller.py) with no
  dependency on AccountPool or ContextStore at all — its constructor takes only a Jules
  client, a session id, and an on_transition(state, activities) callback. Polling is purely
  "watch state, detect transitions, invoke the callback" — what happens in response to a
  transition (releasing an account, saving task state, triggering auto-merge) is entirely
  the caller's responsibility, supplied via that callback, not something the poller resolves
  or constructs on its own. Each caller (coordinator.py, session_runner.py) builds its
  callback closure once, at the point it already has pool/store/whatever else it needs — not
  lazily, not reconstructed per state change.
- The callback contract must preserve every side effect coordinator.py's and
  session_runner.py's existing polling loops currently produce on each relevant transition —
  releasing the account, save_result/save_task_state, setting the completion event
  (coordinator.py); storing activities, triggering auto-merge (session_runner.py) — just
  invoked from the shared engine's callback instead of inline in two separate hand-written
  loops.
- Store activities via whatever Step 2 landed as the local equivalent of _store_activity, for
  every caller uniformly — this is what closes the gap described above.
- Detect terminal states (COMPLETED, FAILED, PAUSED) and AWAITING_PLAN_APPROVAL /
  AWAITING_USER_FEEDBACK (per Step 7 and Step 5's fixes) as first-class transitions the
  callback receives, not just terminal-vs-not.
- Replace the fixed poll interval with adaptive backoff: initial_interval=2.0,
  multiplier=1.5, max_interval=30.0. Not 15.0: for a full-duration (30-minute) session, a
  15.0 cap works out to roughly 123 total polls — worse than session_runner's old flat 15s
  rate (120) and far worse than coordinator's old flat 30s rate (60), which defeats the
  point of this step for exactly the case where call volume matters most. A 30.0 cap works
  out to roughly 66 polls for the same duration — close to coordinator's old, more efficient
  baseline, while still keeping the fast 2.0s start for quick sessions. Optional: add small
  random jitter to each computed interval to avoid multiple concurrently-started sessions
  polling in lockstep.
- Once this exists, Step 5's notify_orchestrator() hook and Step 7's AWAITING_PLAN_APPROVAL
  handling should each need to be wired in one place, not two.

CONSTRAINTS
- This is a structural consolidation, not a behavior change beyond the backoff and the
  activity-storage unification described above — every other state transition coordinator.py
  and session_runner.py currently detect and act on needs to keep being detected and acted on
  exactly the same way, just from one implementation.
- The poller itself never imports or constructs AccountPool or ContextStore.

ACCEPTANCE CRITERIA
- coordinator.py's DAG-task execution and session_runner.py's standalone session execution
  (and therefore mcp/server.py's jat_run_session) all run through the same polling engine,
  with no behavior regressions in any of them — including every existing side effect
  (account release, task state persistence, auto-merge triggering) still firing correctly.
- A short-lived session (completes within the first few seconds) is detected meaningfully
  faster under the new backoff than the old flat-15s interval would have, with a comparable
  or better poll count — not worse.
- A full-duration (timeout-length) session uses meaningfully fewer total polls than either
  old flat interval — verify against actual numbers (~66 vs. session_runner's old ~120), not
  just "fewer than 15s flat."
- coordinator.py's DAG-task path now produces session_activities rows where it previously
  produced none.
- SessionPoller's constructor takes no pool or store argument — verify this structurally
  (e.g. a test asserting its signature), not just by behavior.
- Existing tests for both call sites pass against the consolidated engine.
